This page covers the detailed configuration for [Endpoint Connection](/concepts/product/endpoint-connection) request formatting, response extraction, retry behavior, and conversation end rules.

## Input Template

The Input Template is a [Jinja2](https://jinja.palletsprojects.com/) template string that defines how Galtea formats the request body before sending it to your endpoint.

<Tip>
  For a detailed guide on structured input syntax (`{{ input.field_name }}`), context fields, JSON escaping, the placeholder toolbar, and missing field behavior, see the [Structured Input Template Syntax](/concepts/product/endpoint-connection-template-syntax) reference.
</Tip>

### Available Placeholders

| Placeholder | Description |
|-------------|-------------|
| `{{ input.<field> }}` | Access a field from the test case input, e.g. `{{ input.user_message }}` (required) |
| `{{ context.<field> }}` | Access a field from the test case context, e.g. `{{ context.topic }}` |
| `{{ session_id }}` | The external session ID (if available) |
| `{{ test_case_id }}` | The test case ID |
| `{{ dataset_id }}` | The id of the [Dataset](/concepts/product/dataset) |
| `{{ galtea_session_id }}` | The Galtea session ID |
| `{{ trace_id }}` | The id of this turn's [Trace](/concepts/product/version/session/trace), labeled "Galtea Trace ID" in the dashboard. Also sent automatically as the `X-Galtea-Inference-Id` HTTP header -- useful for [span collection](/sdk/tutorials/tracing-agent-operations) |
| `{{ language_code }}` | Full BCP-47 language tag of the test case, region included (e.g. `"es"` or `"es-MX"`). Empty string when no language is set. |
| `{{ language_name }}` | English name of the test case language, with the region when the tag has one (e.g. `"Spanish"` or `"Spanish (Mexico)"`). Empty string when no language is set. |
| `input_files` | [Files and audio uploaded to Galtea and attached to the test case input](/concepts/product/endpoint-connection-template-syntax#attached-files-and-audio), one entry per Galtea file or audio part. Each exposes `url`, `base64`, `filename` and `mime_type`, e.g. `{{ input_files[0].url }}` |
| Any metadata key | Any field stored in session metadata (e.g., `{{ sessionId }}`, `{{ tenant }}`, `{{ conversation_token }}`) |

<Note>
  `{{ trace_id }}` and `{{ dataset_id }}` were named `{{ inference_result_id }}` and
  `{{ test_id }}` before version 5.0.0, and the old names still resolve. See
  [Dataset, Trace, and Span Renames](/sdk/migration-guides/entity-renames).
</Note>

### Conversation History

Use `{% for turn in past_turns %}...{% endfor %}` to loop through previous conversation turns. Each turn exposes:
- `{{ turn.input }}` — Previous user input
- `{{ turn.output }}` — Previous assistant response

### Attached Files

Use `{{ input_files[0].url }}` to send an attached file to your endpoint, or `{{ input_files[0].base64 }}` to send its bytes inline. See [Attached Files and Audio](/concepts/product/endpoint-connection-template-syntax#attached-files-and-audio) for the full rules, including the 15-minute URL lifetime.

### Examples

**OpenAI-compatible format:**
```jinja2
{
  "model": "gpt-4",
  "messages": [
    {"role": "system", "content": "You are a helpful assistant."},
    {% for turn in past_turns %}
    {"role": "user", "content": "{{ turn.input }}"},
    {"role": "assistant", "content": "{{ turn.output }}"},
    {% endfor %}
    {"role": "user", "content": "{{ input.user_message }}"}
  ]
}
```

**Previous queries array:**
```jinja2
{
  "model": "gpt-4",
  "previous_queries": [
    {% for turn in past_turns %}
    "{{ turn.input }}"{% if not loop.last %},{% endif %}
    {% endfor %}
  ],
  "current_query": "{{ input.user_message }}"
}
```

**Custom format:**
```jinja2
{
  "data": {
    "names": ["query", "contexto"],
    "ndarray": [
      [
        "{{ input.user_message }}",
        [
          {% for turn in past_turns %}
          "{{ turn.input }}",
          "{{ turn.output }}"{% if not loop.last %},{% endif %}
          {% endfor %}
        ]
      ]
    ]
  }
}
```

<Note>
  When a loop is the **last item** in a JSON array, use `{% if not loop.last %},{% endif %}` after each iteration to prevent a trailing comma. When there's content **after** the loop (like in the OpenAI example above), trailing commas are valid and this pattern is not required.
</Note>

## Output Mapping

A JSON object defining how to extract values from the API response using [JSONPath](https://goessner.net/articles/JsonPath/) expressions.

### Special Keys

| Key | Behavior |
|-----|----------|
| `output` | **Required.** The AI's response content. |
| `session_id` | Stored as the external session identifier, accessible via [`custom_id`](/concepts/product/version/session#session-properties). |
| `retrieval_context` | Stored as a `RETRIEVER` span for RAG evaluations (derived at read time, not a directly-readable field). |
| `traces` | Extracts an array of [span](/concepts/product/version/session/span) objects and stores them linked to the trace. Each object should contain at least a `name` field and can include any of the [Span properties](/concepts/product/version/session/span#span-properties): `type`, `description`, `inputData`, `outputData`, `error`, `latencyMs`, `metadata`, `startTime`, `endTime`. A `type` Galtea does not recognize is normalized to a known span type, and your original label is kept in that span's `metadata` under `galtea.span.original_type`. Galtea stores every valid span and drops only the invalid ones, and shows the [dropped count](/concepts/product/version/session/trace) on the trace. |
| `output_files` | Stores each file your endpoint answers with, such as a generated report, as a Galtea file on the turn's output. The path can match one file or a list of files. See [Files in the Response](#files-in-the-response). |
| Any other key | Stored in session metadata and available as `{{ key }}` in templates. |

### JSONPath Syntax Reference

| Expression | Description |
|------------|-------------|
| `$` | Root object |
| `.` | Child operator |
| `[]` | Array index or child operator |
| `[*]` | Wildcard (all elements) |
| `[0]` | First array element |
| `[-1:]` | The last array element, as a one-element list |
| `['a.b']` | A child whose name holds a dot or another special character, e.g. `$.byEvent['response.output_text.delta']` |

Filter and script expressions such as `[?(...)]` and `[(...)]` are refused when you save the mapping, because they would run code on every response.

### Example

```json
{
  "output": "$.choices[0].message.content",
  "retrieval_context": "$.choices[0].retrieval_context",
  "session_id": "$.metadata.session_id",
  "traces": "$.metadata.traces",
  "output_files": "$.files"
}
```

### Files in the Response

Use the `output_files` key when your agent answers with a document: a generated report, a filled form, an image. Galtea stores a copy of each file on the turn's output, so a later read always sees the same bytes. A file that is already in Galtea is linked instead of copied. The stored files appear as the trace's [Output Files](/concepts/product/version/session/trace#param-output-files).

Each file the path matches can take one of three forms:

- **Bytes:** an object with `base64` and optional `mime_type` and `filename`, or a `data:` URI string. The standard and the URL-safe base64 alphabets both work. Galtea decodes the bytes and makes no extra request.
- **URL:** an `http(s)` URL string, or an object with `url` (or `uri`) and optional `mime_type` and `filename`. Galtea downloads the file once, during the run.
- **Galtea file:** the storage URI of a file already uploaded to Galtea, as a string or in `url` or `uri`. It is the signature-free `uri` a written trace or test case reads back with, as stored or under the deployment's public file base when one is set. Galtea links the file on the turn, with no download and no copy. A signed link is read as a URL here, even when it names a Galtea file: it is downloaded and copied. That covers the `uri` an SDK upload returns and the `url` of an `input_files` item.

<CodeGroup>
```json Endpoint Response
{
  "answer": "Here is your quote.",
  "files": [
    { "base64": "JVBERi0xLjQK...", "mime_type": "application/pdf", "filename": "quote.pdf" },
    { "url": "https://files.example.com/quotes/1234/terms.pdf" }
  ]
}
```

```json Output Mapping
{
  "output": "$.answer",
  "output_files": "$.files"
}
```
</CodeGroup>

The text still comes from `output`. A response with files and no text is also a valid turn. An empty value (`null`, `[]`, `{}` or an empty string) means the turn has no file.

The rules:

- **Limits:** at most 20 files and 20 MB in total for one output, Galtea files included. The file extension decides the type, and it must be one a [test case input accepts](/concepts/product/dataset/test-case#file-inputs), such as `pdf`, `docx`, `png` or `csv`. A file with no extension takes one from its `mime_type`, or, for a URL, from the `Content-Type` the file host sends. A name that ends in digits only, such as `invoice_2026.09.23`, counts as having no extension.
- **Download time:** all the URL downloads of one output share one time limit, the connection's [timeout](#timeout). A URL file that has not started when that time runs out is refused.
- **No credentials to the file host:** Galtea sends none of the connection's headers or credentials with the download. A file that needs authentication must come back as bytes, or as a presigned URL that carries its own access.
- **Galtea files belong to your organization:** a Galtea file must be an uploaded file of the organization that owns the product. A file of another organization, or a storage URI that does not name an uploaded file, fails the turn. The same holds for a file that no longer exists.
- **Plain HTTP:** an `http://` file URL is downloaded only when the connection acknowledged plain HTTP, or the deployment allows it for every connection (see [HTTP endpoints](/concepts/product/endpoint-connection#http-endpoints)). Private and internal addresses, such as loopback and cloud metadata, are refused, as they are for the endpoint itself.
- **A refused file fails the turn:** the error names the file and the reason, for example `Output file refused: file 2 ("setup.exe"): the type ".exe" is not allowed`. Galtea stores no file of that turn. When the check Galtea makes before a run already receives a file it would refuse, the run is rejected before it starts.
- **Single-turn runs only:** as with [file inputs](/concepts/product/dataset/test-case#file-inputs), a run of more than one turn fails the turn whose response carries a file. The simulated user reads text only, so the conversation would go on as if the agent said nothing. Run the test case as a single turn, or remove `output_files` from the mapping.
- **Conversation connections only:** Initialization and Finalization connections ignore `output_files`.

The **Test Connection** panel lists the files it finds and shows why a file would be refused. It previews a bytes file and a Galtea file, and it never downloads a URL file. It refuses a Galtea file of another organization, but a Galtea file that no longer exists fails only when a run reads it.

### State Management

If your API returns values that need to be sent in subsequent requests (e.g., `session_id`, `tenant_id`), Galtea can automatically manage this state:

1. **Extract** — Use Output Mapping to pull values from the API response using JSONPath expressions
2. **Store** — Extracted values are saved in the session and become available as template variables
3. **Reuse** — Reference any stored value in the Input Template or URL using `{{ variable_name }}` syntax

<Tip>
  On the first turn, undefined placeholders resolve to empty strings. After the first response, all extracted values become available for subsequent turns.
</Tip>

**Example:** capture `session_id` and `tenant_id` from responses:

<CodeGroup>
```json Output Mapping
{
  "output": "$.text",
  "session_id": "$.session_id",
  "tenant_id": "$.tenant"
}
```

```json Input Template
{
  "role": "user",
  "content": "{{ input.user_message }}",
  "session_id": "{{ session_id }}",
  "tenant": "{{ tenant_id }}"
}
```
</CodeGroup>

### Streamed Replies

If your agent streams its reply, Galtea reads the whole stream and joins its chunks into one object. The Output Mapping then reads that object, so every special key works as on a plain reply. Set two fields on the connection:

- **`streamFormat`**: `SSE` for [Server-Sent Events](https://html.spec.whatwg.org/multipage/server-sent-events.html), or `NDJSON` for one JSON value per line. Leave it empty for a plain reply.
- **`streamAssembly`**: how the chunks become one object. Set both fields or neither: the API refuses one without the other.

In the dashboard form, choose **Streamed reply** and pick your agent stack, or **Custom** to set the fields below yourself. The form sets both fields. On a Conversation connection it also sets the Output Mapping to `$.text` when it still holds the default. An Initialization connection keeps its `session_id` mapping.

| `streamAssembly` field | Description |
|------------------------|-------------|
| `preset` | A named [stream preset](#stream-presets), or `CUSTOM` (the default) to set the fields below yourself. A named preset fills them, and the API refuses it with any of them. |
| `textPath` | **Required with `CUSTOM`.** The JSONPath of the text in each chunk, e.g. `$.choices[0].delta.content`. Use `$` when each chunk is plain text. |
| `mode` | **Required with `CUSTOM`.** `APPEND` joins the text of every chunk, for a stream of deltas. `LAST` keeps the text of the last chunk that has one, for a stream that resends the whole answer. |
| `eventField` | The JSONPath of the event name inside each chunk, e.g. `$.type`. Leave it null to use the SSE `event:` name. A chunk with no name is a `message` event. |
| `terminalEvent` | The event name, or the raw data such as `[DONE]`, that ends the reply. Galtea stops reading there, even if the connection stays open. Leave it null to read until the stream closes. With `SSE`, the event needs a `data:` line, which may be empty. |
| `textEvent` | The only event whose chunks add text, e.g. `response.output_text.delta`. Use it when other events carry a field at the same `textPath`. Leave it null to read text from every event. |
| `errorEvent` | The event name that reports a failure, e.g. `error`. That event fails the turn, with its data in the error. Leave it null to read every event as data. With `SSE`, the event needs a `data:` line, which may be empty. With `NDJSON`, set `eventField` too: an NDJSON line has no event name of its own. |

The Output Mapping reads this object:

| Path | Value |
|------|-------|
| `$.text` | The joined text. |
| `$.byEvent.<name>` | Every chunk of that event, in order, e.g. `$.byEvent.source[*].content`. Use the bracket form for a name with a dot. |
| `$.final` | The last chunk that holds a JSON object or list, e.g. `$.final.conversation_id`. A raw end marker such as `[DONE]` is not kept. |

<CodeGroup>
```json Stream Assembly
{
  "textPath": "$.delta",
  "mode": "APPEND",
  "eventField": null,
  "terminalEvent": "done",
  "errorEvent": "error"
}
```

```json Output Mapping
{
  "output": "$.text",
  "retrieval_context": "$.byEvent.source[*].content",
  "session_id": "$.final.conversation_id"
}
```
</CodeGroup>

- **SSE request header:** for `SSE`, Galtea sends `Accept: text/event-stream` unless a custom header sets `Accept`.
- **Timeout:** the connection [timeout](#timeout) covers the whole stream, not only the first byte. Set it for your longest answer.
- **Idle timeout:** once the agent has started its reply (its response headers have arrived), a stream that sends nothing for 60 seconds fails the turn with an idle timeout, even when the connection timeout has time left. Before that, only the connection timeout applies. Any bytes reset it, so an agent that runs a long tool can send an SSE comment line such as `: keep-alive` to stay live. A self-hosted deployment can change it with `ENDPOINT_STREAM_IDLE_TIMEOUT_SECONDS`.
- **Cut stream:** with a `terminalEvent`, a stream that closes before it keeps the text it sent. The turn is not an error: it is marked truncated in the trace view and in the API (`streamTruncated`), and it is not retried. A cut stream with no text fails the turn. Without a `terminalEvent`, the end of the stream is the end of the reply.
- **Error event:** with an `errorEvent`, that event fails the turn. Like an idle timeout, it is retried with the connection's [retry settings](#retry-configuration) when retry is on.
- **Plain-text tokens in `SSE`:** with `textPath` set to `$`, a token that is a whole JSON string, such as `"sí"` with its quotes, loses its quotes: the text is `sí`. A token that is not a whole JSON string stays as sent.
- **Size limit:** the limit is an approximate memory limit of the assembled reply, 32 MiB by default, not its raw size. Each chunk, and each `{`, `[` and `,` of its JSON, counts 64 bytes more than its size, so a stream of very many tiny chunks or small values reaches the limit sooner. An OpenAI-style stream of one token per event fits about 31,000 events. Each line of an event that has not ended yet, such as an `SSE` event with no blank line after it, also counts 64 bytes until the event ends. A longer stream fails the turn and is not retried. A self-hosted deployment can change the limit with `ENDPOINT_STREAM_MAX_BYTES`.
- **Bad lines:** in `NDJSON`, a line that is not JSON fails the turn and is not retried, unless Galtea stopped reading at the terminal event before that line. Blank lines are skipped. A last line with no line break that is not JSON is read as a cut and dropped.
- **Connection types:** Conversation and Initialization connections can stream. The API refuses both fields on a Finalization connection.
- **Test Connection:** it accepts both fields, reads the stream the same way and shows the joined object. The health check before a run reads it the same way. Both read at most 1 MB of the reply (more when the output mapping reads output files), so a longer stream fails them even though a turn accepts up to the size limit. It reports an idle timeout and an error event with the same message as a turn. For a cut stream it shows the partial text, says it is partial (`streamTruncated` in the API), and gives the same error as a turn when no output came.
- **A stream on a plain connection:** when a connection with no `streamFormat` gets a reply that looks like SSE or NDJSON, the turn and Test Connection say so and name the fields to set.

#### Stream Presets

A preset sets `streamAssembly` for a known agent framework, so you pick its name and add no other `streamAssembly` field. Send `streamFormat` with it:

```json Stream Assembly
{ "streamFormat": "SSE", "streamAssembly": { "preset": "OPENAI_RESPONSES" } }
```

- **Follows the name:** the connection stores the preset name, and Galtea reads its settings at each call. A read of the connection returns `{ "preset": "OPENAI_RESPONSES" }` only. `GET /endpointConnections/streamPresets` lists every preset with its settings.
- **Fixed format:** every preset below streams `SSE`. Set `streamFormat` yourself: the API does not fill it, and it refuses a preset with another format.
- **Your own settings:** to change one field, use `CUSTOM` and copy the preset's settings from the list.
- **Error event:** `OPENAI_CHATKIT`, `OPENAI_RESPONSES`, `ANTHROPIC_MESSAGES` and `VERCEL_AI_SDK` set `errorEvent` to `error`, so that event fails the turn with the vendor's error text. `OPENAI_CHAT_COMPLETIONS` and `GOOGLE_ADK` set none: their documentation names no error event.
- **Refusals:** `OPENAI_RESPONSES` and `OPENAI_CHAT_COMPLETIONS` read the answer text only. A model refusal comes in its own event (`response.refusal.delta`) or field (`delta.refusal`), so such a turn has an empty output. `CUSTOM` reads the refusal alone when `textEvent` is `response.refusal.delta`. With `textEvent` unset, every chunk that matches `textPath` joins the output, so a refusal joins the answer text.
- **Retrieval context:** no preset has a `retrieval_context` mapping, because Galtea has not tested one for these stacks. If your agent sends the passages it retrieved in an event of its own, map them from `$.byEvent`, as in the [example above](#streamed-replies).
- **Source:** each preset is built from the vendor documentation linked below, as read on 2026-11-20. A vendor can change its stream later.

| Preset | Use it for | Output Mapping to start from | Source |
|--------|------------|------------------------------|--------|
| `OPENAI_CHATKIT` | A self-hosted [ChatKit server](https://openai.github.io/chatkit-python/) (chatkit-python). | `output: $.text`, `session_id: $.byEvent['thread.created'][0].thread.id` | [Thread stream events](https://openai.github.io/chatkit-python/concepts/thread-stream-events/) |
| `OPENAI_RESPONSES` | The OpenAI Responses API, or an agent that forwards its stream events, such as one built with the OpenAI Agents SDK. Only `response.output_text.delta` adds text. The reply ends with the stream, so an agent that calls a tool before it answers still gives the whole answer, and `$.final` is its last event. | `output: $.text`, `session_id: $.final.response.id` | [Streaming responses](https://developers.openai.com/api/docs/guides/streaming-responses) |
| `OPENAI_CHAT_COMPLETIONS` | The OpenAI Chat Completions API, or a server compatible with it. The reply ends at `[DONE]`. | `output: $.text` | [Create chat completion](https://developers.openai.com/api/reference/resources/chat/subresources/completions/methods/create) |
| `ANTHROPIC_MESSAGES` | The Anthropic Messages API. The reply ends at `message_stop`. | `output: $.text` | [Streaming messages](https://platform.claude.com/docs/en/build-with-claude/streaming) |
| `GOOGLE_ADK` | A Google Agent Development Kit server at `/run_sse`. Keeps the text of the last event that has one, which holds the whole answer. It reads the first part of that event, so the agent must not send thought summaries. | `output: $.text` | [API server](https://adk.dev/runtime/api-server/) |
| `VERCEL_AI_SDK` | A Vercel AI SDK UI message stream. Only `text-delta` adds text, so reasoning is skipped, and the reply ends at `[DONE]`. | `output: $.text` | [Stream protocol](https://ai-sdk.dev/docs/ai-sdk-ui/stream-protocol) |

**Google ADK** needs a session before the first turn. Create it with an Initialization connection, and send its id in the Input Template of the Conversation connection.

The preset reads the first part of the last event. When the agent sends thought summaries (`include_thoughts=True`), that part is the thought, so the output holds the thought and not the answer. Turn them off, or use `CUSTOM` with the path of the answer part, such as `$.content.parts[1].text`.

**OpenAI ChatKit** creates the thread on the first turn and names it only in that turn's `thread.created` event. The mapping above stores the thread id once. On a later turn the path finds nothing, and Galtea keeps the stored id. Branch the Input Template on `session_id`:

```jinja Input Template
{% if session_id %}{"type": "threads.add_user_message", "params": {"thread_id": "{{ session_id }}", "input": {"content": [{"type": "input_text", "text": "{{ input.user_message }}"}], "attachments": [], "inference_options": {}}}}{% else %}{"type": "threads.create", "params": {"input": {"content": [{"type": "input_text", "text": "{{ input.user_message }}"}], "attachments": [], "inference_options": {}}}}{% endif %}
```

Galtea joins the assistant text deltas of a ChatKit stream. A widget that streams text sends it in the same field, so Galtea joins that text too. A workflow item or a user message adds nothing. When a turn holds two assistant messages, their text is joined with no separator.

## Custom Headers

Custom headers are sent with every request to your endpoint. Header values support placeholder substitution. You can inject authentication credentials, so you can place tokens in any header, not just the standard `Authorization` or `X-API-Key` headers. You can also inject ids of the current call, such as the session ID or the Galtea Trace ID.

### Available Placeholders

| Placeholder | Resolves to | Available when auth type is |
|-------------|------------|---------------------------|
| `{{ auth_token }}` | The authentication token | `BEARER` or `API_KEY` |
| `{{ api_key }}` | The authentication token | `API_KEY` (alias for `{{ auth_token }}`) |
| `{{ bearer_token }}` | The authentication token | `BEARER` (alias for `{{ auth_token }}`) |
| `{{ username }}` | The Basic auth username | `BASIC` |
| `{{ password }}` | The Basic auth password | `BASIC` |
| `{{ trace_id }}` | The id of this turn's [Trace](/concepts/product/version/session/trace), labeled "Galtea Trace ID" in the dashboard. It is not the W3C trace ID in the `traceparent` header | any |
| `{{ galtea_session_id }}` | The Galtea session ID | any |
| `{{ session_id }}` | The external session ID, the one your endpoint returns | any |
| `{{ test_case_id }}` | The test case ID | any |
| `{{ dataset_id }}` | The id of the [Dataset](/concepts/product/dataset) | any |
| `{{ language_code }}` | Full BCP-47 language tag of the test case, region included (e.g. `"es"` or `"es-MX"`). Empty string when no language is set | any |

Placeholders are **case-insensitive** and work with both `{{ placeholder }}` and `{ placeholder }` syntax.

Galtea renders all placeholders of a header value in one pass. A value that does not exist yet renders as an empty string. For example, `{{ session_id }}` is empty until your endpoint returns a session ID. A rendered value is never scanned for placeholders again.

Which context placeholders hold a value depends on the call:

| Call | Context placeholders with a value |
|------|-----------------------------------|
| Conversation turn | All six. `session_id` is empty until your endpoint returns one |
| Initialization | `galtea_session_id`, and `session_id` when the session already has one |
| Finalization | `galtea_session_id`, and `session_id` when the session has one |
| Test connection | Sample values for all six |

Every other context placeholder renders empty in that call.

<Note>
  Header values carry Latin-1 characters only. A value with other characters, for example a `session_id` that holds them, fails the call. A value with a line break fails the call too.
</Note>

### Example

```json
{
  "Authorization": "Bearer {{ bearer_token }}",
  "X-Custom-Api-Key": "{{ api_key }}",
  "X-Galtea-Session": "{{ galtea_session_id }}",
  "X-Tenant-Id": "my-tenant"
}
```

<Tip>
  If you define an `Authorization` or `X-API-Key` header in custom headers, Galtea will **not** add the default authentication header — your custom header takes precedence.
</Tip>

### Secret Header Values

Galtea treats a header value as a secret unless one of these is true:

- The header name is `Content-Type`, `Accept`, `Accept-Language`, `Accept-Encoding`, `Cache-Control`, `User-Agent`, `traceparent`, or `tracestate`.
- The value holds only placeholders, with an optional `Bearer`, `Basic`, or `Token` prefix (for example `Bearer {{ bearer_token }}`).

Galtea encrypts each secret value when you save the connection, and sends the real value to your endpoint. The Dashboard, the API, the SDK, and the CLI show a secret value as `••••••••`.

Galtea binds a connection's stored secrets (auth token, password, and secret header values) to the origin they were saved for. The origin is the scheme, the host, and the port. The path does not count, and `http` to `https` on the default ports is the same origin. The exception is a stored URL with a template placeholder in its host: its origin is unknown until send time, so only the identical URL counts as the same origin, and a change of path alone clears the stored secrets. The binding covers saving and testing a connection. A real call that your endpoint redirects to another host is not covered yet.

A test of a saved connection sends the stored secrets only to that origin, and returns what the endpoint answers. While the connection holds a saved secret, a test with a URL of another origin fails with a `400` error and sends nothing. Another path on the same origin still works, except when the stored URL has a template placeholder in its host: that origin is unknown until send time, so only the identical URL passes.

A test of a saved connection needs permission to edit it, for any URL. A member who can only view the connection gets a `403` error.

When you save a new URL with another origin, Galtea clears the stored auth token, password, and secret header values. Send the new token or password in the same request. Headers that are not secret stay. A URL with a template placeholder in the host is refused while the connection holds a secret, and so is the first secret written to such a row. A move to another origin clears the stored secrets first, so only a secret sent in the same request counts. A rename or a token rotation that leaves the URL alone still works.

In the example above, only `X-Tenant-Id` is a secret. A header imported from a cURL command, such as `CF-Access-Client-Secret`, is a secret too.

To change a connection's headers, send the whole map again:

- Keep `••••••••` as the value of a header to keep its stored value. After a new URL with another origin, this fails with a `400` error, because Galtea cleared the stored value: type the new value.
- Type a new value to replace it.
- Remove the header to delete it.

A `••••••••` value for a header that has no stored value is rejected with a `400` error. An encrypted value is also rejected with a `400` error: send the plain value instead. So is a value that only looks like `••••••••`, such as `••••••••abc`: keep the exact value, or type the whole new one.

### W3C Trace Context Propagation

Galtea sends a `traceparent` header on every conversation turn call, following the [W3C Trace Context](https://www.w3.org/TR/trace-context/) specification. It does this whether or not the platform's own tracing is on, and on every retry of the turn. You do not need to set anything up. Your endpoint can correlate its spans with the turn without any code changes.

- Each turn has one trace ID. Every retry of the turn sends the same trace ID.
- Galtea stores the trace ID on the turn when the turn starts, before it calls your endpoint. A span your agent exports before it answers attaches to the turn.
- Galtea never sends the header on initialization, finalization, or test-connection calls.
- Galtea sets the header itself. Galtea refuses a `traceparent` header in custom headers on save (400).

<Note>
  The header is flagged as sampled. An agent with a parent-based sampler records every Galtea test call, so expect more trace volume in your own tracing backend.
</Note>

See [Spans of a Trace that already exists](/sdk/tutorials/send-opentelemetry-traces-to-galtea#spans-of-a-trace-that-already-exists) for how Galtea matches your spans to the turn, and [How span content maps to Span records](/sdk/tutorials/send-opentelemetry-traces-to-galtea#how-span-content-maps-to-span-records) for how they become Span records.

### Baggage

Galtea also sends a W3C `baggage` header on every conversation turn call:

```
baggage: galtea.trace.id=<turn id>
```

The value is the id of the turn, the same one as `{{ trace_id }}`. If you set your own `baggage` header, Galtea merges its member into yours. Your other members stay. A `galtea.trace.id` member you set is replaced.

An agent that copies baggage onto its spans attaches every span to the turn, even when a proxy or gateway starts a new trace and changes the trace ID. To copy baggage onto spans, use the OpenTelemetry baggage span processor for [Python](https://pypi.org/project/opentelemetry-processor-baggage/) or [JavaScript](https://www.npmjs.com/package/@opentelemetry/baggage-span-processor). Both accept a key predicate. Use one that copies only keys that start with `galtea.`.

<Warning>
  An agent instrumented with OpenTelemetry forwards baggage to every service it calls, including LLM providers and other third parties. So the turn id can leave your agent. The id is opaque: nobody can read or write anything with it without a Galtea API key of your organization.
</Warning>

Python OpenTelemetry drops a `baggage` header longer than 8192 characters. Galtea's member adds about 60 characters, so keep your own baggage well below that limit.

## Timeout

How long Galtea waits for a single HTTP call to your endpoint before giving up. It is applied **per attempt**, so each retry gets the full timeout again.

<ResponseField name="Timeout" type="Number">
  Per-attempt request timeout in seconds. Default: `15`. Maximum: `120` (values above this are rejected at the API).
</ResponseField>

For a [streamed reply](#streamed-replies), it covers the whole stream.

A timeout counts as a retryable failure. If retry is enabled, a timed-out call is retried like any other transient error.

## Rate Limit

The maximum number of requests per minute your backend can handle. Galtea throttles itself to stay under this limit, using a token bucket shared across all of Galtea, so the limit holds even when many runs execute at once.

<ResponseField name="Rate Limit" type="Number">
  Maximum requests per minute. Default: empty, which means **no limit** (no throttling). Set a number only if your backend needs Galtea to slow down.
</ResponseField>

When the limit is reached, Galtea reschedules the call for later. This wait does not use up a retry attempt and does not block other runs.

## Retry Configuration

Configure automatic retry behavior for failed requests. When enabled, Galtea retries requests that fail with a retryable HTTP status code, a timeout, or a network error. On a [streamed](#streamed-replies) connection, an idle timeout and an error event are retried too. A retry wait does not block other runs: the job is rescheduled and the worker is freed while it waits.

<ResponseField name="Retry Enabled" type="Boolean">
  Whether automatic retry is enabled. Default: `true`
</ResponseField>

<ResponseField name="Max Retry Attempts" type="Number">
  Maximum number of retry attempts (`0`-`10`). Default: `1`. These are retries **after** the first call, so N attempts means up to N+1 calls to your endpoint, and **each call uses credits** (the default of 1 means up to 2 calls). `0` is only valid when retry is disabled; with retry enabled the minimum is `1`.
</ResponseField>

<ResponseField name="Initial Delay" type="Number">
  Initial delay in milliseconds before the first retry. Default: `1000` (1 second)
</ResponseField>

<ResponseField name="Backoff Strategy" type="Enum">
  Strategy for increasing delay between retry attempts:
  - `exponential` - Delay doubles with each attempt (recommended)
  - `linear` - Delay increases linearly
  - `fixed` - Constant delay between attempts

  Default: `exponential`

  The delay is always capped at **Max Delay**. With a small Max Delay, exponential and linear growth are clamped to that ceiling after the first retry, so the strategy has little effect. Raise Max Delay to let the delay grow.
</ResponseField>

<ResponseField name="Max Delay" type="Number">
  Maximum delay between retry attempts, in milliseconds. Default: `3000` (3 seconds). Capped at `60000` (60 seconds); values above this are rejected at the API.
</ResponseField>

<ResponseField name="Retryable Status Codes" type="Array of Numbers">
  HTTP status codes that should trigger a retry. Default: `[429, 500, 502, 503, 504]`. Each value must be a valid HTTP status code (`100`-`599`).

  Codes are honored literally with no client-error short-circuit. Adding a deterministic `4xx` code (such as `401`, `403`, or `422`) makes Galtea retry a call that will always fail, which wastes the full retry budget and the credits for each attempt.
</ResponseField>

## Conversation End Rules

Some agents end a conversation on their own and then answer every further message with an error. Without a rule, Galtea reads that error as a failed turn, so the session fails. Its evaluations are then skipped because of the failed turn. A conversation end rule tells Galtea which reply means "the agent ended the conversation". On a match, the session completes with the turns so far and is evaluated.

A rule has a status code and an optional body match. Default: no rules. A connection holds at most 20 rules, and only a `CONVERSATION` connection accepts them.

<ResponseField name="Status Code" type="Number">
  HTTP status code of the reply (`100`-`599`). A `2xx` code needs a body match, because a `2xx` rule without one would end the conversation after the first normal reply.
</ResponseField>

<ResponseField name="Body JSONPath" type="Text">
  Optional. A JSONPath into the response body, starting with `$` (for example `$.error.code`). See [JSONPath Syntax Reference](#jsonpath-syntax-reference). Filter expressions such as `[?(...)]` are refused.
</ResponseField>

<ResponseField name="Expected Value" type="Text">
  Used when a Body JSONPath is set. The first value the path finds must equal this text. An empty Expected Value matches an empty string.
</ResponseField>

### Example

After your agent closes the conversation, it answers every further message with HTTP `409` and this body:

```json
{"error": {"code": "conversation_ended", "message": "This conversation has ended."}}
```

The rule is status code `409`, Body JSONPath `$.error.code`, and Expected Value `conversation_ended`. A `409` with any other `error.code` does not match, so it still fails the turn as before.

### How a reply matches

- Galtea checks the rules **before** the [retry policy](#retry-configuration). A matching reply is never retried, even when its status code is in Retryable Status Codes.
- A reply matches when the status code is equal and, if the rule has a body match, the first value the JSONPath finds is a string, number, or boolean whose text equals the Expected Value. So the number `42` matches the Expected Value `42`.
- A missing field, an object, an array, `null`, or a body that is not JSON never matches.
- On a [streamed](#streamed-replies) connection, the body of a `2xx` reply is the joined object, so the path reads `$.text`, `$.byEvent` or `$.final`. The body of any other status stays as your agent sent it.
- Rules apply only to the conversation calls of text sessions. Initialization and finalization calls, voice sessions, and the connection test ignore them.

### What happens to the session

- **A 2xx match with an agent answer**: the reply is a normal agent reply, so that turn stays as the last turn and is scored. This also holds on the first turn and in a single-turn test.
- **A match with no agent answer**: a non-2xx match (such as the `409` above), or a 2xx match whose reply has no output. The rejected turn holds the simulated user message and no agent reply. Galtea removes that turn, so it is not scored.
- In both cases the session completes with the stopping reason `The agent ended the conversation (HTTP <code>)`, for example `The agent ended the conversation (HTTP 409)`, and is evaluated.
- A match with no agent answer on the first turn, or in a single-turn test, still fails the session, because there is no conversation left to evaluate.
