## SDK Creates Say When the Record Was Stored

When the platform stores a new record but cannot return it, an SDK `create` now raises `WrittenResourceUnreadableException` instead of returning `None`. The record exists, so do not create it again: read it with the service's `get` or `list` method. See [Errors](/sdk/api/galtea#errors).

## Install an Older CLI With Any Package Manager

APT and DNF now keep every CLI release from 4.24.0, as PyPI already did, and Homebrew keeps the newest patch of each minor version. You can install the CLI that matches an older Galtea platform with the tool you already use. When a CLI is too new for its platform, it now prints the install command for every tool. See [Install an older version](/cli/installation#install-an-older-version).

## LLM Judges Skip Turns That Carry a File

On deployments that do not send files to the judge, an LLM-as-a-judge metric, custom judge metrics included, now ends **Skipped** when a turn it reads carries an attached file, and the reason names the file. Before, the judge scored the turn's text alone, so the score could describe a document the judge never saw. DeepEval-based and classifier metrics still score the text. See [Troubleshooting skipped evaluations](/concepts/metric/evaluation-parameters#troubleshooting-skipped-evaluations).

## See and Open Voice and File Outputs the Same Way

The [agent's answer](/concepts/product/version/session/trace) now gets the same file and voice marks as the input. The evaluations table's Output column, the sessions table's Last Output column and the evaluation conversation summary show a file or voice icon beside the answer's text, and name the file when the answer is only a file, instead of an empty cell. The full-text dialog lists the answer's files and plays its audio.

## See All Your Products at a Glance

The top of the organization's products page now sums up the products the table shows: how many sessions came in, how many were evaluated, and how many of those had no issues, minor issues or a critical failure. It also shows the estimated AI model cost per session and in total, and lists the products whose share of critical failures went up the most, each linking to its analytics. The boxes follow the period, the view mode and the name and tag filters. The same numbers are available with `galtea analytics get-sessions-overview`, `get-cost-overview` and `list-changes`.

## Text Content Parts Count as Text

When a turn's input or output holds `{"type": "text", "text": ...}` content parts, the judge, monitors, `past_turns` and the dashboard now read their text, next to `user_message` or `assistant_message` and any other fields. Before, that text could be lost, or the judge got the whole value as JSON. In the SDK, `.input`, `.actual_output` and the message `traces.generate` sends now include this text, and an audio-only value gives its transcript instead of `None`. An output's other fields are now scored beside `assistant_message`. Every CSV export of an input or output now writes the stored value as it is, so you can import the file again. See the **Input** field of a [trace](/concepts/product/version/session/trace#trace-properties).

## Only owners manage billing

Only an organization owner can now change the plan, open the billing portal or buy extra credits. Members still see the plan. See [Roles and permissions](/security/roles-and-permissions).

## See Which Product Needs Attention

The organization's products page is now a table that shows, for each [product](/concepts/product), how many sessions came in, how many were evaluated, how many failed a [critical specification](/concepts/product/specification), and whether that rate got worse than in the period before. It also shows the estimated cost per session. Pick the period at the top right: by default it covers the last 30 whole days, today included. Sort by most columns, filter by name or tag, and pin the products you follow so they stay first. Click a row to open the product's analytics. The same numbers are available with `galtea analytics list-products`.

## Retirement Emails Name the Evaluator Model

The retirement warning now arrives as "Action needed: an evaluator model used by your metrics is retiring", and the notice after the date speaks of evaluator models too. Each email suggests other [models](/concepts/model) of the same kind you can move to. To list the models of one kind, pass `kind` to `GET /evaluatorModels` (`LLM_JUDGE` by default); each model now also returns its `kind`.

## Mark a Specification as Critical

You can now mark a Capability or Policy [specification](/concepts/product/specification) as critical, when its failure is serious for your business. Use the **Critical** switch in the dashboard, `is_critical` in [`specifications.create()`](/sdk/api/specification/create), or `galtea specifications update` for an existing one. Critical specifications show a red **Critical** pill, and the **Critical** filter lists only them or only the others. [`specifications.list()`](/sdk/api/specification/list) filters the same way. When the AI writes a specification for you, it also suggests the Critical flag, and you can change it before you save.

## Each CLI Version Has a Fixed Set of Commands

The [CLI](/cli/usage) now carries the commands of its own release, instead of downloading them from the API. An API update can no longer change your commands or flags between two runs. To get new commands, update the CLI. `galtea sync` now does nothing and will be removed, and `GALTEA_CACHE_TTL` has no effect, so take both out of your scripts. See [Getting new commands](/cli/usage#getting-new-commands).

## The SDK Checks That It Works With Your Platform

When you create the `Galtea` client, the SDK now checks that its version works with the Galtea platform it calls. If it does not, it stops and tells you which version to install. This matters most on a self-hosted platform: a newer SDK than the platform supports now stops at start-up, so install the version the message names. The CLI shows the same information with `galtea platform-compatibility`. See [Upgrading the SDK](/sdk/installation#upgrading-the-sdk).

## See and Sort Sessions by Number of Turns

The sessions table has a new **Turns** column with the number of turns in each [session](/concepts/product/version/session), deleted turns left out. Click its header to sort the filtered list. Sorting works on up to 50,000 sessions: for more, narrow the list with the **Created At** or **Status** filter first. In the API, `GET /sessions` returns `turnCount` and can sort by it.

## The Simulated Caller Stops When Your Voice Agent Cuts In

On a [phone connection](/concepts/product/phone-connection), and now also on a [WebRTC connection](/concepts/product/webrtc-connection), the simulated caller stops talking within about one second when your agent makes a sound over it. A short sound such as "mm-hm" is enough. The turn keeps only the audio that was played, and its transcript is cut to match it as closely as possible.

## Large Evaluation Runs Wait Out Rate Limits

When an evaluation run goes over a judge model's per-minute quota, Galtea now waits for the quota to free up, for up to 5 minutes, instead of failing the evaluation. Large runs end with fewer failed [evaluations](/concepts/product/version/session/evaluation). If the provider asks for a longer wait, the evaluation still fails at once.

## Unlink Rows by Unchecking Them or From the Row Menu

In the link dialogs of a [specification](/concepts/product/specification) and of a [user group](/concepts/user-group), rows that are already linked now show as checked. Uncheck a row and click **Save links** to unlink it. Unlinking never deletes the row itself.

- **Row menu:** a specification's **Datasets** and **Metrics** tabs offer **Unlink from specification** on each row, and a group's **Products** tab offers **Unlink from group**. In a group's **Products** tab, the row item asks you to confirm first, because the group's users lose access to the product.
- **No Delete in linked lists:** the row menu of a specification's **Datasets** and **Metrics** tabs and of a group's **Metrics** tab no longer offers **Delete**, so one misclick cannot delete a dataset or a metric.

## Voice Turns With Extra Fields Are Scored on What Was Said

When a voice turn's input has your own fields next to the audio, for example a `language` field, the judge now reads the spoken transcript first, then those fields. Before, it could score the turn on your fields alone. When no turn of a session has text, a metric that reads the input is now skipped instead of scored. See the **Input** field of a [trace](/concepts/product/version/session/trace#trace-properties).

## The Dashboard Picks Up User Group Changes Without a Reload

When an admin changes your [user groups](/concepts/user-group), the dashboard now applies your new access when you come back to its browser tab, at most once every 30 seconds. New products appear, and a page that was denied opens. If you lose access to the product you have open, you land on the organization's **Products** tab.

## Creating From a User Group Tab Links the New Entity

A user, metric or product you create from inside a [user group's](/concepts/user-group) own tab now joins that group automatically, instead of landing unlinked.

- **Users tab:** the invite form opens with the group pre-selected, in the Advanced options.
- **Metrics tab:** a blank metric starts as Human Evaluation with the group selected. The form clears the group when you switch to any other metric type, and puts the tab's group back when you return to Human Evaluation — a different group you picked before switching away is not kept. Starting from a template or revision keeps that source's own groups and adds this one.
- **Products tab:** the name field notes which group the new product will join.

This only happens when you have the right to link that group (`userGroup.update`), and it is dropped the moment you navigate to a plain creation page instead of the group tab. The [SDK's `metrics.create`](/sdk/api/metric/create) also takes an optional list of group ids to link on creation; there is still no `products.create` in the SDK. Creating a metric from the AI generation tab of the metric creation page does not link a group yet.

## JSON Field Match Checks a Field by Rule

A [JSON Field Match](/concepts/metric/json-field-match) test case can now give a field a rule instead of an exact expected value, by writing an object with a `$` key: `$norm` (same text once accents, case, spaces and every other character that is not a letter or digit are dropped), `$regex` (an RE2 pattern, case-insensitive by default), `$num` (a decimal comparison within a `tol` tolerance) or `$date` (reads common date formats, with an `order` of `DMY`, `MDY` or `any`). The same four rules work the same way across the [strict](/concepts/metric/json-field-match-strict), [normalized](/concepts/metric/json-field-match-normalized) and [normalized-strict](/concepts/metric/json-field-match-normalized-strict) variants.

A rule field shows as a neutral "Rule" row in the evaluation details, rather than a red mismatch, and it isn't counted as a difference. A test case with a broken rule (an invalid pattern, an unknown option, or a pattern too large to run) skips the evaluation instead of failing it, with no retry.

This release also changes what happens when the expected or actual output itself can't be read, for every JSON Field Match evaluation, rule or not: an expected output that isn't valid JSON, or output nested too deeply, now skips the evaluation instead of failing it as a platform error. If you track pass rates against past FAILED counts for this metric, expect some of those to move to skipped going forward.

## See and Open Voice and File Inputs the Same Way

The sessions table's First Input column, and the evaluations table's session-wide Input column, now show the caller's first turn instead of the agent's opening greeting, scanning up to the first three turns of the [session](/concepts/product/version/session). In the evaluations table, an input with nothing to show — including a single-turn evaluation whose input is an empty envelope — now leaves the cell blank, matching the Output column, instead of showing a dash. The same empty input exports as an empty CSV cell.

Audio inputs get the same voice icon [files](/concepts/product/version/session/trace) already had, shown even next to a transcript, and alone when there is none. A cell holding only audio or only a file, in the sessions, evaluations or test case tables, now carries the same hover button a long text cell has, so one click opens the player or the file instead of the cell being a dead end. Long file names are truncated with an ellipsis instead of spilling into the next column.

## Import LangSmith Dataset Exports as Sessions

**Import traces** now accepts a LangSmith dataset export (JSONL), as well as a Langfuse export. Each conversation becomes one closed [session](/concepts/product/version/session), and each example one turn. In the dashboard, choose the file type in the new **Format** field before you import. In the API, `POST /sessions/import` takes an optional `format`, and detects the format from the file when you leave it out. [Import sessions from a trace export](/concepts/product/version/session#import-sessions-from-a-trace-export) explains how examples are grouped.

## The Best Version Is Shown in Bold in Comparison Tables

In the version comparison tables of the specification and metric analytics, the best version of each row is now in bold, instead of carrying a grey pill. Every row keeps the same height. A row with only one scored version shows no best version.

## Members See Only the Products of Their User Groups

A Member now sees and works only in the products that their [user groups](/concepts/user-group) grant, like a Reader and a Human Evaluator already did. Nobody loses access with this change: every existing Member was added to a group that grants all products. Owners and Admins are not affected.

- **A new Member with no group sees no product** until an Owner or Admin adds them to a group. The invite and edit user forms warn before they leave a Member with no group.
- **Only a Member in a group that grants all products can create a product.**
- **Metrics stay shared:** a Member still reads and edits every metric of the organization.

[Roles and permissions](/security/roles-and-permissions) lists what each role can do.

## Evaluations Cut Off by the Token Limit Are Skipped, Not Failed

When a metric's `max_output_tokens` is too low for the judge to finish its answer, the [evaluation](/concepts/product/version/session/evaluation) is now **Skipped**, with a reason that names the limit. Before, it **Failed** as a platform error. To fix it, create a revision of the metric with a higher limit and evaluate again. A metric now needs a `max_output_tokens` of at least 256, to be created or optimized: see [`metrics.create()`](/sdk/api/metric/create).

## The CLI Works Behind a Gateway That Serves Galtea Under a Path

The [CLI](/cli/usage) now works when your API gateway serves Galtea under a path, such as `https://gw.example.com/org/galtea`, and your key comes from `GALTEA_API_KEY`. Before, the CLI showed no API commands in this setup. Pass the full URL, path included, to `--host`, as [Behind an API gateway](/cli/usage#behind-an-api-gateway) shows.

## Build a Monitor Step by Step, with Its Cost in View

The create and edit forms of a [monitor](/concepts/product/monitor) now follow the order a session travels through it: **Filter sessions** first, then **Sampling and cost**. The [preview](/concepts/product/monitor#preview) walks the same funnel, from the closed sessions in the read window, to the ones that pass your filters, to the sampled share, ending in `≈ N credits per month` with `capped at N` when your credit cap is lower, and the `N sessions × N credits each` behind it.

- **Pick sessions by how many messages they hold.** A monitor takes up to 10 conditions, joined with AND, each comparing `messages` (user and agent) or `user_messages` using `lt`, `lte`, `eq`, `gte` or `gt` against a value from 0 to 200. In the SDK, pass `message_conditions` to [`monitors.create()`](/sdk/api/monitor/create) and [`monitors.update()`](/sdk/api/monitor/update). It replaces `min_user_messages`: a stored `0` becomes no condition, and a stored `N` becomes `user_messages gte N`. A new monitor starts at `messages gt 1`, so a session holding a single agent turn with no reply is skipped.
- **Conditions no session can meet are refused.** `messages gt 5` together with `messages lte 3` is rejected on create, update and preview, and the dashboard disables **Enable monitor** and **Preview** while the rows contradict each other.
- **The form lists the specifications and metrics you chose**, and the catalog opens in a dialog from **Add specifications or metrics**. The one-time **Add from Specification** metric copy is gone.
- **Save as paused** stores a new monitor without starting it. Coverage is forward-only: a monitor never scores sessions that predate it, and resuming it does not go back over the sessions that arrived while it was paused.
- **Turning the credit cap on prefills 15% of your organization's monthly credit plan**, instead of a flat 5000. The 5000 remains the prefill when that plan is unknown.

## Analytics Shows What Has Not Been Evaluated

A specification, metric or version with no score now reads **Not evaluated** on a dashed, empty track, so it no longer looks like a zero. Both the Development and Production views now list every specification that links at least one metric, and every metric, that your filters still allow, rather than only the ones that happened to be scored. The specification picker of the Metrics section offers the unscored specifications too.

In the version comparison tables, a version with no score for a listed row gets its own **Not evaluated** cell instead of being dropped from the row. The tables still list only rows that at least one version scored; the bar view is where an entirely unscored specification or metric appears.

The selected version's detail column adds **Coverage**: how many of its test cases were evaluated, as a count and a percentage, split into Evaluated, Not evaluated and Total, and measured against the most-evaluated version where there is one. A **Coverage by version** table below the charts gives a row per compared version it has coverage for. Both appear only for roles whose permissions include analytics coverage, so a reader or human evaluator does not see them.

## Every Score Names the Evaluations Behind It

Each score in the Scores panel, on the specification and metric bar charts, and in the version comparison tables now shows `passed X/Y` beside it, so you can tell a strong result from one backed by a handful of evaluations. A score built from fewer than 10 evaluations is muted, with a tooltip saying it is weak evidence. The Average Score carries no count, since it counts each metric once however many evaluations it holds.

The count is one per evaluation, not per test case. A specification with 5 metrics on 2 test cases therefore counts 10 evaluations and is not muted, though it covers only 2 test cases. Read it with the [coverage](/concepts/product/monitor#seeing-production-scores-across-the-whole-product) figures above.

## Manage a User Group from Its Own Tabs

The **Users** and **Metrics** tabs of a [user group](/concepts/user-group) now link and unlink, instead of only creating. **New User** becomes a menu with **Link existing user** and **Create new user**. The Metrics tab gains **Link existing metric**, which offers Human Evaluation metrics only, and replaces **Delete** with **Unlink from group**, which confirms first and leaves the metric itself in place. A metric that already holds evaluations, and a Human Evaluation metric that belongs to no other group, cannot be unlinked. On the Products tab, **Link products** becomes a **Register Product** menu, and its dialog shows the products the group already has as checked and not selectable, with an **Already linked** tooltip. The group list adds a **Products** column that reads the number of linked products, or **All**.

## Send Custom Headers Through an API Gateway

When Galtea sits behind an API gateway that expects headers of its own, both the SDK and the CLI can now send them.

In the SDK, pass `headers` to `Galtea()`, or set `GALTEA_EXTRA_HEADERS` to a JSON object, as described in [Custom API URL and headers](/sdk/installation#custom-api-url-and-headers). The argument replaces the environment variable rather than merging with it. They travel with every API call and with span exports. `authorization`, `user-agent`, `content-type`, `content-length` and `host` are dropped with a warning, a malformed name or value raises an error while the client is built rather than on the first call, and no header follows a redirect to another origin. File uploads and downloads go to signed storage URLs, which do not carry them.

The CLI reads the same `GALTEA_EXTRA_HEADERS`, and keeps headers held on its `default` profile for the host you logged into, merging the two per key with the environment variable winning a clash. See [Behind an API gateway](/cli/usage#behind-an-api-gateway). Login sends them too, and a gateway that refuses the call before the API sees your key is now reported as the gateway's own rejection, apart from a rejected API key.

## Documentation and Examples

A new guide covers the [Claude Code tracing plugin](/sdk/integrations/claude-code-tracing): installation, its options, what each conversation sends, redaction, when a session closes and reopens, and how to stop logging. An interactive conversation arrives as a production session and each turn as a trace, with model calls, tool calls and subagents as spans, so a [monitor](/concepts/product/monitor) can score a sample of those sessions as they close. One-shot runs, such as `claude -p` and the Agent SDK's `query()`, are not logged.

Each session also lands on a version named after the model of its first answer, which gives its turns a cost. That cost is an estimate at list prices: every model call of a turn, subagents included, is priced at the main model's rates, and cache writes are left out. A model name Galtea does not know gets no price, and a Galtea that refuses the version, such as an older self-hosted one, puts the session on the product's latest version with no cost at all.

## Platform Improvements

- **A monitor edit saves while it holds a metric that is no longer active.** Only a metric family you add needs an active metric, so renaming a monitor or changing its sampling no longer fails over a family that is retiring, disabled or deleted. The form and the monitor's own reads name each family and its state — **Retiring**, which still scores, **Disabled** or **Deleted** — instead of showing a raw id. A monitor whose families have all been deleted still reads as Active and scores nothing.
- **The Development view of Analytics opens on the latest versions over all time.** On a product with more than five versions that have results, it compares five: the four newest, plus the version with the highest total average score, or the fifth-newest when the best is already among them. A removable **Latest versions + best** pill marks it; remove the pill to compare every version. The Production view keeps its own defaults.
- **The Scores comparison radar card is gone from Analytics**, and the Coverage card takes its column.
- **The Analytics Scores panel paginates**, 10 rows to a page with the page kept in the URL, instead of scrolling inside the panel. Changing the sort, grouping, filters or view returns you to the first page.
- **The comparison tables keep their rows when you highlight a version**, instead of blanking to loading rows.
- **The Analytics metrics filter tells same-named metrics apart.** A repeated name gains a suffix: `Galtea` for a Galtea metric, with its status when Galtea metrics share the name, or the status and creation date for one of your own. Labels that still match add the last six characters of the metric id.
- **The Ask Val launcher lifts clear of a button at the end of a page** instead of covering it, by up to half the window height. A control it covers mid-page still needs a scroll.
- **A deprecated SDK call names its removal date in the warning it raises**, so you can plan the upgrade. One with no date set yet says `Removal: not scheduled.` Deprecations the platform owns, such as legacy metrics, carry no date.

## Link a Dataset to Several Specifications

A [dataset](/concepts/product/dataset) can now link to more than one [Specification](/concepts/product/specification) of the same product, as long as they share the same dataset type (Accuracy, Security, or Behavior). Before, linking a dataset to a new specification silently dropped its old link.

- **The dataset details page lists every specification it links to.** Each one opens its own page.
- **The edit form lets you add or remove links.** Changing the list shows an **Edited** badge you can click to undo.
- **Running an evaluation on several specifications that share a dataset scores it once**, with the combined metrics of every specification in that run. Running it from one specification's page still scores the dataset with only that specification's metrics, [even when the dataset links to others too](/concepts/product/specification#specifications-and-datasets).
- **In the SDK**, pass `specification_ids` to [`datasets.create()`](/sdk/api/dataset/create) and [`datasets.update()`](/sdk/api/dataset/update). The older `specification_id` still works but is deprecated and only remembers the oldest link. Agent runs need SDK 5.11.0 or later to honor every link; an older SDK only reads the oldest one.

## Analytics Opens as a Worst-First Table

The product Analytics page now opens its Specifications, Metrics, and Inference sections as a table, so you can scan every score without reading a chart. Specifications and Metrics sort worst score first; Inference keeps its usual row order, since latency, cost, and token counts are not directly comparable. Click a row to open that specification's or metric's page. Switch back to Bar Chart from the view selector: your choice is remembered across a refresh or a shared link, and the default Table view does not clutter the URL.

## Dashboard Shows Only the Actions You Can Use

The dashboard now shows a write action, and opens a create or edit page, only when your role allows it. A reader or human evaluator no longer sees buttons they cannot use: a page they cannot open now shows a clear access-denied message, and a review mark or score they cannot change shows as plain text instead of a control. The platform assistant's write-approval card checks the same [permissions](/security/roles-and-permissions): when your role cannot do what it proposes, the card explains why and offers only **Dismiss**.

## Platform Improvements

- **Invited people get the Galtea invitation email.** Before, Keycloak's own "Update your account" email went out instead of "Welcome to Galtea! You have been invited to join the Galtea platform." The sign-in link does not change.
- **The monitor form now shows a specification's metric families correctly** even when a specification links a family only through an older metric revision. Before, such a family showed as empty or disabled in the form, though the monitor already [scored it correctly](/concepts/product/monitor#metric-families-follow-revisions-automatically).
- **A provider's content block now ends an evaluation with a clear reason**, telling you to pick a different evaluator model, instead of a generic failure. In the Val assistant, a block partway through an answer now ends the reply with a clear error instead of cutting it off with no explanation.
- **Creating or updating a dataset now returns the full dataset**, not just its id, so you do not need a follow-up read. Organization, product, and dataset writes also accept `Prefer: return=minimal` when you only need the id, or no body, back.

## Link One Dataset to Several Specifications

A [dataset](/concepts/product/dataset) can now link to several [Specifications](/concepts/product/specification) of its product. An evaluation that names several of them runs the dataset once and scores it with the metrics of all of them.

- **In the SDK**, pass `specification_ids` to [`datasets.create()`](/sdk/api/dataset/create) and [`datasets.update()`](/sdk/api/dataset/update). `specification_id` is deprecated and holds the oldest link.
- **Agent runs need SDK 5.11.0 or later.** An older SDK reads only the oldest link of a dataset, so [`evaluations.run()`](/sdk/api/evaluation/run) with an `agent` skips a dataset linked to several specifications for every specification but its oldest one.

## Alert Rules Can Watch a Whole Specification

A monitor's [alert rule](/concepts/product/monitor#alert-rules) can now watch one [Specification](/concepts/product/specification) the monitor binds, not only one metric family.

- **Pick a Specification or a metric.** The rule form's **Watches** field has **Specifications** and **Metrics** tabs. It opens on **Specifications** when the monitor binds one with a scored metric; you cannot switch tabs once the rule exists. Add one rule per target to watch several.
- **A session fails the rule when any metric the Specification brings fails it**: a score at or below the bad metric score, or, for a "Sessions get no score" rule, an evaluation that settles with no score. A session that fails two of the Specification's metrics still counts once. See [Rules on a Specification](/concepts/product/monitor#rules-on-a-specification).
- **The rule follows the Specification.** Link a new metric to it and the next check watches that metric too, with no rule edit.
- **If the Specification later brings no scored metric, the rule stays and opens no new alert.** You can still edit it; the form warns and names the fix. An alert already open keeps recovering on the metrics it measured when it opened.
- **The rule list gets a Watches column**, and the rule page names its Specification or metric in its condition. The alert and webhook payloads name the Specification and the metrics that caused it.

## See the Specification and Criteria Behind a Score

An evaluation's [Verdict card](/concepts/product/version/session/evaluation) now shows which Specifications the score answers and what the judge graded it on, so a reader who did not write the metric can judge the score on the same card.

- **A Specification line** above the metric names the [Specifications](/concepts/product/specification) of the evaluation's product that link the metric, each linked to its page. One shows its description; several show the count and names.
- **A Criteria panel**, closed by default, opens on the full metric description, then the classifier question with its good answer, or the judge prompt, rendered as Markdown.
- **The panel header names the revision** that produced the score: its creation date, its metric id, and a status pill (Legacy, Disabled) when that revision is no longer active.

## Platform Improvements

- **Specification lists load their dataset counts past 20 rows.** A dashboard filter sent array ids as indexed query parameters (`ids[0]=a&ids[1]=b`), which the API's query-string parser silently turned into an object above 20 ids and rejected with a 400; the specifications list showed "Missing dataset" on every row once a page passed that count. Array filters now go out as repeated keys, the form the API publishes and the SDK already sends.
- **Picker dialogs no longer hide their create button.** The Endpoint Connection, Phone Connection, WebRTC Connection and Model pickers, and the Specification and classifier Session pickers, now give their toolbar a title row, so the dialog's close button no longer sits on top of the button beside it.

## One Filters Menu for Every Table and for Analytics

Every table that has filters, the trace Spans list, the monitor alert history and the Analytics page now open them from one **Filters** button.

- **One row per filter.** Each value shows as a pill that you remove with its ×. A badge on the button counts the active filters.
- **Remove all filters** clears the filters, text searches included, and puts a filter that has a default back on that default. On alert history the default time range is **Last 7 days**, which always shows as a pill.
- **The same 9 time ranges everywhere.** Table date filters such as **Created At**, alert history and Analytics list Last hour, 6 hours, 12 hours, 24 hours, 7 days, 30 days, 90 days, Last year and Last 2 years beside the calendar. A range moves with the clock: "Last 7 days" in a saved link means the 7 days before you open it. Dates picked in the calendar stay fixed.
- **Analytics keeps its filters in the URL.** The time range, datasets, versions, metrics and languages survive a reload, and a shared link opens with them. **Group by** stays outside the menu.

On Analytics, the default time range is **Last 2 years**. **Remove all filters** there widens it to all time, not to the default. A link with an unknown range, with dates over 5 years apart, or with the dates in reverse order opens on the default. See [Seeing production scores across the whole product](/concepts/product/monitor#seeing-production-scores-across-the-whole-product).

## Set the Score That Counts as a Pass for Each Metric

Every [metric](/concepts/metric#pass-threshold) now has a pass threshold: the score, from 0 to 1, at or above which an evaluation passes. Metrics without one keep 0.5, so existing results do not change.

- **Set it at creation.** In the dashboard, pick the evaluation type, then set **Pass threshold (%)** under **Advanced Options**; a new metric starts at 50. In the SDK, pass `pass_threshold` to `metrics.create()`. The API takes `passThreshold`. It is fixed once the metric exists: create a revision to change it, and the revision starts with the threshold of its source.
- **Read each verdict.** An [evaluation](/concepts/product/version/session/evaluation) now carries `passed` and the threshold it was judged at: `metric_pass_threshold` in the SDK, `metricPassThreshold` in the API. `passed` is null when the evaluation has no usable score. Score pills in the dashboard are green at or above the threshold and red below it.
- **Filter by verdict.** The evaluation lists have a **Result** filter and a hidden **Result** column, which the CSV export includes. In the SDK, `evaluations.list(passed=True)` keeps the evaluations that passed. The API takes `passed=true|false` on `GET /evaluations`.
- **Optimization follows the threshold.** The optimizer judges at the metric's pass threshold, and an optimized revision keeps it.

## Review Human Evaluations One After Another

The **Human Evaluations** page is now a hub with three tabs: **Evaluate**, **Pending** and **Submitted**. You need the human evaluation or human annotation permission, and a user group, to see it. See [Annotate in the Dashboard](/sdk/tutorials/human-evaluation#step-6-annotate-in-the-dashboard).

- **Score without a dialog.** The **Evaluate** tab opens your next pending evaluation and reserves it for you. Click **Save & Next** to submit and move on, or **Skip** to give it back to the group.
- **Pick a verdict.** The score starts on **Incorrect**, **Partially correct** or **Correct**, stored as 0, 0.5 and 1. Switch to **Percentage** or **Fraction** for any other [human evaluation](/concepts/metric/evaluation-types#human-evaluation) score.
- **Keep the guidelines in view.** On a window at least 64rem wide and 37.5rem tall, the guidelines, score, reason and buttons stay on the right while the conversation scrolls on the left.
- **Attach evidence.** Select a phrase in the conversation, click the evidence icon, and write a note. The **Evidence (N)** button next to **Reason** lists them for edit or removal. Evidence is saved as text at the end of the reason, so `human_reason` in the SDK returns it too. Only the **Evaluate** tab offers evidence, not the Manual Evaluation dialog.
- **Limits.** Your reservation ends when you leave the tab or close the browser. Otherwise Galtea releases it between 2 and 2.5 hours after you took it. Through the API, releasing an evaluation that you already submitted now answers 400 and keeps you as its author.

## Alert When a Monitor's Sessions Get No Score

A [monitor](/concepts/product/monitor) alert rule can now warn you when evaluations stop producing scores.

- **Pick "Sessions get no score"** under **Alert when** in the monitor's **Alerts** tab. The API type is `NO_SCORE_RATE`. Set **Threshold (%)**: a percent above 0 and at most 100, with a default of 20.
- **A session counts when its latest evaluation failed or was skipped and has no score**, a classifier "Does not apply" answer included. Pending and cancelled evaluations do not count, and a human score counts as a score. On a metric where "Does not apply" is normal, set the threshold above that normal rate.
- **The rule needs at least 5 evaluated sessions in its window** before it opens or closes an alert. Until then, an active rule shows a **Waiting** status and a note with the session count. Through the API, a `NO_SCORE_RATE` rule carries the same counts in `readiness`, which is null when Galtea cannot read the count.
- **The alert closes** at the threshold minus its square root, rounded down: a 10% rule closes at 6%.
- **Limit:** a failed evaluation counts in the window in which it was created, not when it failed, and an evaluation that never finishes does not count.

**Action needed if you call the alert-rule API directly.** `POST /monitors/{monitorId}/alert-rules` now answers 201 with only `{ id }`; read the rule with a `GET`. Update, pause and resume now answer 204 with no body. See [Rule types](/concepts/product/monitor#rule-types).

## Send Monitor Alerts to a Webhook or a Slack Channel

A [monitor](/concepts/product/monitor) alert rule can now post to a webhook URL, next to or instead of its email recipients.

- **Add a Webhook URL to a rule** in the monitor's Alerts tab, or send `webhookUrl` through the API and the CLI. A rule holds one URL, and now needs at least one email address or a webhook URL.
- **Galtea sends one signed `POST` when an alert opens and one when it recovers.** The JSON body carries the same fields as the alert email, with up to 25 session links. When a delivery times out or gets a 408, 429 or 5xx answer, Galtea tries again, up to 6 attempts in about 5 minutes. Any other error stops the delivery at once.
- **A Slack incoming-webhook URL shows a readable message**, with links to the alert and, when it opens, to up to 10 sessions. Mattermost and Rocket.Chat show the same message from the `text` property.
- **The URL is write-only.** The dashboard and the API show only its host, and its port when it is not the default. An address in a private network is refused.
- **Check the signature.** Each rule has a secret. In the dashboard, tick **Show the signing secret after saving** when you save the URL; on a rule that already has one, the box reads **Show a new signing secret after saving** and replaces the secret. Through the API or the CLI, `POST /monitors/{monitorId}/alert-rules/{alertRuleId}/regenerate-webhook-secret` or `galtea monitors regenerate-alert-rule-webhook-secret` returns a new secret. See [Webhooks](/concepts/product/monitor#webhooks).

## Monitor a Product by Its Specifications

A [monitor](/concepts/product/monitor#binding-specifications) can now score the metrics that your Specifications link, not only metrics you pick one by one.

- **Bind Specifications.** In the monitor form, select them on the **Specifications** tab. In the API, send `specificationIds` on `POST /monitors` or `PATCH /monitors/{id}`. In the SDK, pass `specification_ids` to `monitors.create` or `monitors.update`. `metric_group_ids` is now optional.
- **The monitor scores both sources.** It scores the families you picked plus the families of each bound Specification. Read the full set in `scoredMetricGroupIds`; `metricGroupIds` keeps only your picks.
- **It follows the Specification.** When you link or unlink a metric on a bound Specification, the monitor scores the new set from its next scan.
- **Updates replace the list.** `specificationIds` on an update replaces the bound Specifications. When an update removes a family from the monitor, its alert rules are deleted.
- **Policy and Capability only.** A monitor refuses an Inability or a Specification of another product, and a bound Specification cannot become an Inability.
- **Some metrics are skipped with no error:** Self-Hosted metrics, metrics that cannot score production sessions, and Classifier metrics while they are off.
- **The empty-scope check runs only on save.** If a bound Specification later loses its metrics, new sessions are not scored, and an alert rule on that family opens no alert.
- **The form shows current metric revisions only**, so it can show fewer families than the monitor scores.

## Route OpenTelemetry Traces to a Product and Version

A collector that sends only standard resource attributes, such as `service.name` and `service.version`, now reaches the right product and version. See [How Galtea Routes a Trace](/sdk/tutorials/monitor-real-user-traffic-with-opentelemetry#how-galtea-routes-a-trace).

- **Find the product by its key.** The organization lists 1 to 10 resource attributes that identify a product. A new organization uses `service.name`. Each product gives its own value for each attribute (`otelProductKeyValues`), and it can use its own key instead. A trace must carry every attribute of the key, and matching is exact. When several products match, the key with the most attributes wins, and a tie routes nowhere.
- **Find the version by its attributes.** The organization lists up to 32 resource attributes, and a product can replace that list. Galtea finds or creates the [version](/concepts/product/version) whose facts are the listed attributes that the trace carries. The list is empty until you set it.
- **Set it** on the new **OpenTelemetry** card of the **Update Organization** page and in **Advanced Options** of the product edit form, or with `PATCH /organizations/{id}` and `PATCH /products/{id}` (`galtea organizations update` and `galtea products update` in the CLI).

Limits and changes:

- **`PATCH /products/{id}` and `PATCH /organizations/{id}` now refuse unknown fields** with an error, where the product route ignored them before.
- **Two products cannot hold the same key values**, and the organization cannot change its key attributes while a product that follows the key holds values. Both answer `409`.
- **A trace that matches no product is rejected**, with the reason in the response's `partialSuccess`.
- **Routing happens once, at ingestion.** A later settings change moves no stored trace.

## Attach Files to a Trace Input

A [trace](/concepts/product/version/session/trace) you log yourself can now carry the documents your agent received. Galtea stores and keeps them like the files of a [test case input](/concepts/product/dataset/test-case#file-inputs).

- **Pass `input_file_paths`** to [`traces.create`](/sdk/api/trace/create), [`traces.update`](/sdk/api/trace/update) or [`traces.create_and_evaluate`](/sdk/api/trace/create-and-evaluate). Each entry is a local path, which the SDK uploads, or a Galtea storage reference such as `trace.input_files[0].uri`.
- **`input` is optional when you pass files**, except in `traces.create_and_evaluate` with `session_custom_id` and only a `product_id`.
- **Galtea keeps the files.** On S3 storage, the cleanup of temporary uploads no longer removes them, and the stored reference does not expire.
- **The test case rules apply.** The SDK allows at most 20 files and 20 MB in total. When an input holds a Galtea file, the API also checks the limits, the file types a test case input accepts, and that every file belongs to your organization, and refuses a trace that breaks a rule.

Limits to know:

- **Evaluators cannot read input files yet.** A metric that reads the input is skipped when no turn of the session has input text without a file. To have a turn scored, log the text your pipeline extracted as the input, without the file.
- **`traces.update` replaces the whole input.**
- **The SDK refuses a URL outside Galtea storage.** A direct API call stores such a URL as sent, with no check, unless the same input also holds a Galtea file: then the API refuses it.
- **An OpenTelemetry turn whose input breaks a rule is dropped.**

## Get Emailed When a Monitor Scores Badly

A [monitor](/concepts/product/monitor) can now raise an alert when too many sessions score badly, and email people about it.

- **Add alert rules in the monitor's Alerts tab,** or through the API and the CLI (`galtea monitors create-alert-rule`). The SDK has no alert methods.
- **A rule holds** a metric, a window of 15 minutes, 1 hour, 6 hours or 24 hours, a bad metric score, a threshold and 1 to 20 recipient emails. The dashboard prefills 0.5 and 10. The API and CLI require both values. The recipients need no Galtea account.
- **Every 2 minutes Galtea counts the bad sessions.** A session is bad when its score is at or below the bad metric score. It counts once, by its latest score on that metric inside the window. Only evaluations made by that monitor count.
- **The alert opens when the count reaches the threshold,** and recovers when it falls to the threshold minus its square root, rounded down. With a threshold of 10, that is 6. A window with no scored sessions leaves the alert as it is.
- **Recipients get an email when an alert opens and another when it recovers,** with links to up to 25 sessions. A deployment with no email configured sends none.
- **Deleting or pausing a rule closes its alert and sends no email.** So does changing its metric, bad score or window, which also checks the rule again at once. Editing only the threshold keeps the alert open.
- **Follow alerts in the dashboard.** A rule shows OK, Open or Paused. A monitor page offers alert history with filters, and each alert has a page listing the evaluations behind it.
- **Pause and resume a monitor** with [`monitors.pause()`](/sdk/api/monitor/pause) and [`monitors.resume()`](/sdk/api/monitor/resume), `galtea monitors pause`, or the dashboard. A paused monitor scores no new sessions. Its open alerts stay open once the window holds no scored sessions. You can pause a single rule too.
- **A monitor can no longer take a self-hosted metric.** Creating a monitor with one, or adding one, is refused. Existing monitors keep theirs, and those metrics are skipped.
- **Removing a metric from a monitor deletes the alert rules on that metric.**

## Review an Optimized Judge Prompt Before It Replaces Your Metric

- **The candidate waits as "Ready for review"** with the changes, the optimized prompt and the original prompt in tabs. **Apply optimization** makes it the active revision. It keeps the original's current name, description and tags, and copies its specification and user-group links. **Keep original** marks it "Not applied" and changes nothing.
- **A declined candidate cannot be applied later.** A metric holds one waiting candidate at a time, and applying or declining needs permission to update the metric.
- **An unchanged prompt ends as "No improvement".**
- **While an optimization runs,** monitors score only the original metric.
- **Your annotations are split before the run.** With at least 30 annotated evaluations, about one third of them (at least 10) are held out, chosen by session. The optimizer never searches on them. The confirmation shows the split. The review shows how well each prompt agrees with your annotations on both sets.
- **Below 30 annotated evaluations there is no held-out set,** unless an earlier attempt on the same metric kept some. The review says when it has no validation result.
- **Only an organization-owned AI Evaluation metric that is the active revision can be optimized.** The SDK has no optimize method. Use the dashboard, the CLI or the API.

## Every Launch Now Leaves a Run

A [run](/concepts/product/run) is the record of one launch. Galtea creates one every time you launch evaluations, from the dashboard, the CLI, the SDK or the REST API. A queue job disappears; a run stays, so you can still read last week's launch.

- **Find runs under Runs in the product sidebar,** behind **More** unless **Show all tabs** is on. A run's page has four tabs: **Overview**, **Launches**, **Sessions** and **Evaluations**. Outside the Production view, session and evaluation tables gained a **Run** column and a **Runs** filter.
- **A run whose test cases produced no session ends as `FAILED`,** with its reason. Sessions and no evaluations is still a success: a generation with no metric ends `COMPLETED` and carries no score.
- **Run again** repeats a run and answers with a new one, leaving the original alone. The button is hidden, not disabled, when a run cannot repeat: two launches of one kind, no evaluation naming a session, or over 1000 sessions. For a run your own code drove, it re-scores the existing sessions rather than producing new ones. Only a re-launch accepts a different `versionId`.
- **Cancel a queued launch** without stopping the rest of the run. A launch that finishes inside the request that started it cannot be cancelled. Whatever it already created is kept.
- **Each run carries a number**, shown as `#42`, starting at 1 in each product. A deleted run keeps its number, so gaps are normal.
- **Group several launches in one run.** Open a run, pass its id to each launch, and close it when they are done. `fromMetrics` and `fromTestCases` take no `runId` and open their own runs, and a run you opened yourself records no version.
- **Python SDK:** [`galtea.runs`](/sdk/api/run/service) offers `start()`, `list()`, `get()`, `get_by_custom_id()`, `close()` and `delete()`. [`start()`](/sdk/api/run/start) returns a context manager, so sessions and evaluations created inside a `with` block join the run. The write methods also take `run_id` directly, and [`evaluations.list()`](/sdk/api/evaluation/list) filters by it.
- **[CLI](/cli/usage):** `galtea runs list`, `get`, `create`, `close`, `relaunch`, `cancel-launch`, `get-metric-summary` and `delete`.

**What joins no run, and says nothing about it:** a production session, which the API refuses a `runId` for and the SDK leaves out of a `with` block; a [monitor](/concepts/product/monitor) evaluation; a retry, which keeps the run it started in; work you start on another thread inside the block; and a session `get_or_create` finds rather than creates. A `with` block also cannot close a run holding a queued launch. It raises instead and asks you to call `runs.close()` once the launch ends. Deleting a run leaves its sessions in place.

## Start a Test Case Mid-Conversation

A `SCENARIOS` [test case](/concepts/product/dataset/test-case) can now start from a conversation that already happened. The simulator continues from that point instead of opening the dialogue itself. Use it to test what your agent does on turn five, not only on turn one.

- **Two ways to give the conversation.** `conversationHistory` writes the turns out. `seedSessionId` copies them from an existing session, with its [spans](/concepts/product/version/session/span), so it carries the retrieval context and tool calls the written form cannot. Sending both is refused.
- **Live Turns to Run counts only the new turns.** A 4-turn conversation with **Live Turns to Run** set to 1 ends with 5 turns. The field is `max_iterations` in the SDK and in a CSV file.
- **Set `userPersona`, `goal` and `scenario`, or the run fails on its first live turn.** Nothing checks them when you save the test case. An `input` carrying files fails the same way.
- **Not on voice yet.** A phone or WebRTC run ignores the conversation and starts from turn one.
- **`simulate(agent_goes_first=True)` is refused** on a seeded test case, after your agent's opening turn is recorded. The session keeps that turn and produces no score.

## Configure the Judge That Scores Your Metric

An AI Evaluation [metric](/concepts/metric) can now name the generation settings its judge runs with, and prompt-based evaluations report what the judge spent.

- **Prompt judges no longer run at `temperature: 0` by default.** Galtea used to apply it implicitly, and that is removed. Existing metrics were backfilled with an explicit `0`, so they are unchanged. A **new** metric created without a temperature now follows the provider's own default and is less deterministic. Set `temperature` yourself to keep the old behavior.
- **Four settings are accepted:** `temperature`, `top_p`, `max_output_tokens` and `reasoning_effort`. Set them when you [create the metric](/sdk/api/metric/create), in the **Model settings** section under the evaluator model picker or through `judge_generation_settings` in the SDK. Any other key is refused.
- **Only `FULL_PROMPT` and `PARTIAL_PROMPT` metrics use them.** A DeepEval metric fixes its own temperature and ignores the settings, so many built-in Galtea metrics cannot be tuned this way and report no tokens.
- **The form offers only what your model accepts,** and a model can accept none of the four. A setting your model does not accept is dropped when the judge runs and the evaluation still succeeds, so nothing tells you it had no effect. A *value* your provider rejects is different: that evaluation ends `SKIPPED` carrying the provider's own message. List what a model accepts with `galtea evaluator-models list`.
- **`reasoning_effort` is free text.** The levels differ per model: `minimal`, `none` and `max` exist beside `low`, `medium` and `high`.
- **`Max output tokens` is capped by your model's ceiling in the dashboard only.** The API accepts any whole number of 1 or more, so an SDK or CLI caller can store a value the model will not honour.
- **Settings cannot be changed later.** Create a revision of the metric to use different ones. The dashboard carries them into the revision, keeping those the new model also accepts. Through the SDK, a revision that omits them gets none.
- **Prompt-based evaluations now record the judge's token usage.** The evaluation page shows it in a card under the **Verdict**, and the evaluation list offers **Judge Tokens**, **Input Tokens**, **Output Tokens**, **Reasoning Tokens** and **Token Distribution** columns. The Python SDK returns the counts on `Evaluation`. Reasoning tokens sit inside the output count, so never add all three together.

## Choose What Counts in Your Analytics

You can now exclude a [metric](/concepts/metric) revision from analytics, and read the Scores card in the order that answers your question.

- **Exclude a revision from analytics.** Its results leave the score, coverage and insight numbers, and keep their own score and reason. Evaluation totals, latency, cost and token figures still count them. Before, analytics pooled every revision, so a stricter replacement diluted the current score.
- **The exclusion is organization-wide, not per product.** One action changes every product holding results from that revision.
- **Excluded results are then hidden by default,** in the evaluation list, in the metric list and in the SDK. Turn on **Show excluded from analytics**, or pass `include_excluded_from_analytics=True`. The metric list's **Analytics** column is hidden until you reveal it.
- **A legacy revision still counts.** Creating a revision marks the previous one `Legacy`, and only an exclusion stops it counting. After you save a revision, the dashboard says how many results and products the earlier one affects, and keeps them by default. Excluding is a separate request, so it can fail on its own and leave the revision saved and still counted.
- **The decision is reversible** from the metric's actions menu, and it changes no evaluation. You cannot exclude a Galtea platform metric, and a read-only account cannot exclude anything.
- **A product's Analytics page says how many results sit outside the reported numbers,** and links to them. There is no way to read analytics with them added back.
- **Python SDK:** [`metrics.set_analytics_exclusion()`](/sdk/api/metric/set-analytics-exclusion) and [`metrics.get_analytics_exclusion_impact()`](/sdk/api/metric/get-analytics-exclusion-impact).
- **The Analytics Scores card draws bars instead of rings, lowest score first.** A picker beside the heading switches to `Highest first` or `A to Z`, and your choice rides the URL. It appears once the card holds two bars.

## Compare the Expected Output Against the Actual One

The [evaluation](/concepts/product/version/session/evaluation) details page now shows the expected output beside the actual one, and the expected tools beside the tools that were called.

- **A JSON payload reads as a per-field table,** one row per path, marked `Match`, `Similar`, `Differs`, `Type mismatch`, `Missing`, `Unexpected` or `Length differs`. Matching rows hide behind a toggle that names how many it holds back. A large payload stops at 500 rows.
- **Fields, Pretty and Raw.** A payload with fields offers all three. A short label or plain prose offers Pretty and Raw only, and the tools card carries no view controls at all.
- **Each payload carries its own view controls,** so you can read one output as **Raw** while the page stays **Pretty**. That override is not saved: a reload returns every payload to the stored setting.
- **Raw is the only view of the stored characters.** Fields and Pretty read the scored value, which unwraps `assistant_message` and content parts.

The comparison opens on its own when the metric declares an expected output, both values are present, and the product is `PROGRAMMATIC` or `HUMAN_DIRECT`. Everywhere else, including a conversational product, the **Diff** switch in the card header reaches it in one click.

## Read Every Attached File in Place

A file attached to a turn now carries **Full size**, **Expand** and **Download** wherever the turn itself is shown, so checking an extracted field against its source stays on one screen.

- **Expand** opens the file under its row, and **Full size** opens it in a lightbox. **Download** is still there for anything stored.
- **A PDF renders inline,** next to the output and the verdict, without leaving for a download or another tab.
- **An image gets the same controls,** for the formats a browser renders: `.png`, `.jpg`, `.jpeg`, `.gif`, `.webp` and `.bmp`.
- **A single file opens on its own** when the whole conversation is one turn and that file is one the platform can preview.

Two limits. A file the platform cannot show in place, such as a `.docx`, a `.csv` or a TIFF, keeps the download alone. And a file listed in a table cell carries no controls, so open the session or the evaluation to reach it. Judges never read an attached file, whatever it shows.

## Every Version Now Has a Number

Each [version](/concepts/product/version) carries a number, unique inside its product and starting at 1. `v7` is the label Galtea derives from it.

- **A version with no name shows its canonical label.** The dashboard shows `v7`, or `v7: support release` when the version carries a custom name. Galtea no longer invents a name for the first version it creates for you.
- **`v` followed by digits is a reserved name shape.** `v28`, `v01` and `v0` are all refused, unless the name is that version's own label. A name such as `v1.0` stays valid.
- **A name is no longer unique inside a product.** A version named `v5` before numbering and the product's fifth version can now stand side by side, so `versions.get_by_name` may raise `AmbiguousVersionNameException`.
- **Numbers are not contiguous.** Deleting a version leaves a permanent gap.
- **Python SDK:** `Version.number` is on the response model, and `versions.create(product_id=...)` now works with no name. `number` is optional, and the label falls back to the bare name when it is absent.

## Reach Every Product Section From the Sidebar

**Datasets**, **Sessions**, **Evaluations**, **Runs** and **Tutorial** appeared only when **Show all tabs** was on, so most readers never saw them listed.

A **More** entry now sits after the other work entries and opens those five in a menu. Each item is a real link, so you can middle-click it into a new tab. In the Production view, Datasets is absent and **More** holds four. Turn **Show all tabs** on and the five render inline, with the **More** row gone. The setting lives in your browser, so it does not follow you to another device. Two sections also left the setting in this release: **Connections**, now development-only, and **Monitors**.

## OpenTelemetry: Mark Test Traffic, and Name the Real Turn Input

Three changes for products instrumented with plain [OpenTelemetry](/sdk/tutorials/send-opentelemetry-traces-to-galtea) and no Galtea SDK.

- **Mark a trace as test traffic** with the `galtea.test_case.id` attribute, on the resource or on a span, where a span attribute wins. The session it opens is then non-production and linked to that test case, so a [monitor](/concepts/product/monitor) never scores it. Before, every ingested session was production, so development traffic reached your production monitors. Three things to know: a value that is not a non-empty string is ignored in silence and you get a production session, exactly as if you sent nothing; a marked session stays `PENDING` until you widen the product's auto-close scope or close it yourself; and only OTLP ingestion reads the attribute, so file import and `POST /traces/batch` ignore it.
- **Name where the turn input lives** with `otelInputSourceRule`, per product or per version, when your [spans](/concepts/product/version/session/span) carry no recognised input attribute. Galtea used to fall back to the LLM span's messages array, which is your system prompt plus a copy of the user message, so the judge scored the reply against a prompt your user never wrote. `otelOutputSourceRule` does the same for the output. Two limits: when the rule finds nothing, the turn input is empty, because the old fallbacks no longer apply; and a version cannot opt out of a product rule.
- **A batch missing `galtea.version.id` now logs one warn line per sender,** so you can find the sender environment to fix. The export response and the dropped-span counter name the reason but not the sender.

## Platform Improvements

- **Invite someone who already has an account:** inviting a registered address now moves that person across, when they are alone in their organization, that organization has a free plan or none, the invite names no user group, and neither side uses an enterprise IdP. They get an email naming the organization and the role, and confirm from a page within 24 hours. The move is final: their old organization stays behind unreachable, with its products, evaluations and credits, and their API keys start writing into the new one. Outside those conditions the invite fails as before.

A blank Authentication Token keeps the stored credential, as long as you do not change the authentication type. A blank username still overwrites.
- **One SDK exception for a missing entity:** a read of an entity the platform does not hold now raises `EntityNotFoundException`, importable as `from galtea import EntityNotFoundException`, whether you read by id or by name. Nothing forces you to migrate: a 404 raises a subclass of both that and `requests.HTTPError`, so existing `except requests.HTTPError` code keeps working. - **Generated scenarios stay grounded:** a scenario generated from a conditional specification is now built on a catalog record the rule governs, and Galtea picks one itself when the planning model names none. When no record matches the rule, the scenario falls back to the whole catalog and the guarantee does not apply.

## Review Evaluations and Correct a Wrong Judge Score

Finding where your judge disagrees with your reviewers, and fixing it, now happens in one place and counts everywhere.

- **A [metric](/concepts/metric) page is now a hub** with three tabs: **Details**, **Revision History**, which draws every revision of the metric and how they descend from each other, and **Evaluations**, which lists every evaluation the metric produced across every product that used it.
- **See the disagreement directly.** The **Evaluations** tab shows the judge's score, the reviewer's score, and the **Score gap** between them in points. The [evaluation](/concepts/product/version/session/evaluation) page gained a **Verdict** card that puts both side by side with their reasons, and says when they disagree on pass or fail.

- **It applies to reviews you already made,** so some numbers change as soon as this release is live, without you doing anything.
- **More evaluations can carry a review:** one that failed, was skipped, or was cancelled now counts once a reviewer scores it. Before, only a successful one did.

## Send Attached Files and Audio to Your Agent

A test case that attaches a document, an image, or audio can now run end to end without leaving Galtea. Creating a product that reads PDFs, scanned receipts, spreadsheets, photographs, or screenshots is supported too, and the product form now says so instead of warning you off.

- **Platform runs:** your endpoint connection reads attachments through a new `input_files` collection in its template, with four properties per file: `url`, `base64`, `filename`, and `mime_type`. See the [template syntax](/concepts/product/endpoint-connection-template-syntax).
- **Python SDK:** an agent called through `evaluations.run`, `simulator.simulate`, or [`traces.generate`](/sdk/api/trace/generate) receives each attachment as an `InputFile` object, instead of a raw dictionary buried in the message metadata. Read one into memory with the new [`galtea.storage.read()`](/sdk/api/storage/read), or see [reading attached files](/sdk/api/agent/input).
- **Dashboard:** an input holding only files used to render an empty cell. It now names the files, and a download saves under the real filename instead of the storage key.
- **Video is not supported yet,** and a product that processes video recordings or live video is now named as such rather than left unclear.

Limits to plan around: **20 MB** per input, at most **20 files**, 22 accepted extensions, a download link valid for **15 minutes**, and one turn per platform run. Evaluators still cannot read the file itself, so a metric needing the input is skipped unless you also log readable text as the turn input. A template reading `{{ input.content[0].uri }}` no longer returns an address, so use `{{ input_files[0].url }}`. The [document inputs tutorial](/sdk/tutorials/evaluate-document-inputs) covers the full path.

## Version 5.0.0: A Redesigned Dashboard

This release reworks how you navigate and use the dashboard: the sidebar, specification setup, evaluation flow, and onboarding all change, and three core entities get clearer names. Here is what moved and why.

## New Names: Dataset, Trace, and Span

Three entities you use every day change their name, so each level of the platform now has one clear word:

- **Test** is now [**Dataset**](/concepts/product/dataset): the collection of test cases you evaluate a version against.
- **Trace** is now [**Span**](/concepts/product/version/session/span): one step your product took while answering, like a tool call or a retrieval.
- **Inference Result** is now [**Trace**](/concepts/product/version/session/trace): one input and the output your product returned.

A [session](/concepts/product/version/session) now holds traces, and a trace holds spans. `Test Case` keeps its name; only the collection around it becomes a dataset.

The API, CLI, SDK, and dashboard all use the new names. If you call the platform through the SDK or CLI, read the [migration guide](/sdk/migration-guides/entity-renames) before you upgrade. In the SDK, most old names keep working with a warning, and you can pin `galtea<5` to delay the change. Two things need your attention: `galtea.traces` now returns traces instead of spans, so it changes meaning without an error, and the CLI has no aliases. Pinning does not help the CLI either, because it reads its command names from the API and refreshes them on its own. Update your CLI calls before the release.

## Redesigned Sidebar Navigation

The sidebar now carries most of what used to live in page tabs.

- **A product selector and environment switch sit at the top**, so you pick your product and switch between Development and Production without leaving the sidebar.
- **A product's sections list directly in the sidebar**, replacing the product hub's top tab strip. Analytics, Specifications, and Versions are always there; Datasets, Sessions, Evaluations, and Tutorial appear once you turn on **Show all tabs** in your settings. The configuration sections, Product, Connections, and Monitors, sit inside a collapsible **Configuration** folder, marked with a caret so you know it expands rather than opens a page.
- **The organization hub is now the landing page** after login, with Products as its first tab and a product count next to Users and Groups. The product matching your sidebar selection is outlined in that list, so you can tell them apart at a glance.
- **Organization-level entries** (organization settings, Human Evaluations, Metric library) **now group at the sidebar's bottom**, under your organization's own name.
- **Your account menu moved into a floating card** at the sidebar's bottom, instead of a page of its own.

## Monitor Only the Production Traffic That Matters

A [Monitor](/concepts/product/monitor) scores a sampled share of your production [sessions](/concepts/product/version/session). The new **Content filter** section of the create and edit form tells it *which* sessions are worth scoring at all: refund and cancellation traffic for a support agent, everything except your internal test phrases for a medical assistant.

- **Include and exclude terms.** **Include terms** keeps only the sessions containing one of your terms. **Exclude terms** drops the sessions containing one of them, even if they matched an include term. Both are optional.
- **Write terms the simple way.** Separate terms with a comma, for example `refund, cancel, chargeback`. A session matches when any term appears anywhere in a turn, and matching is case-insensitive.
- **Choose which side of the turn to search.** Each group has its own **Match in** setting: the user's `Input`, your product's `Output`, or `Either`.
- **See the effect before you save.** A **Preview** panel tests the filter against your recent sessions and spends no credits: how many contain your terms, roughly how many would be evaluated at your current sampling percentage, and which ones match, so you can click into one and check.

Two limits to know. Sampling applies on top of the filter, so you get roughly your sampling percentage of the *matching* sessions, not of all traffic. And the filter only affects sessions that close after you save it, never past traffic. A Monitor's **Overview** tab states its filter in plain language.

Content filters work in the dashboard and on `POST /monitors` and `PATCH /monitors/{id}`. The Python SDK does not set them yet, so a Monitor created with [`monitors.create`](/sdk/api/monitor/create) has no filter until you add one in the dashboard.

## Monitor Your Production Traffic Automatically

Testing tells you an AI product is ready to ship. **Monitors** tell you it is still behaving once real users arrive. A [Monitor](/concepts/product/monitor) is an always-on evaluation rule: point it at a [product](/concepts/product), pick the [metrics](/concepts/metric) that matter, and Galtea keeps scoring your live production sessions on its own. There is no run to trigger, no schedule to maintain, and no extra code once your product logs its sessions.

This is the difference between finding a quality regression in a weekly report and catching it as it happens. A Monitor watches the traffic your users actually send, so a drop in answer quality, a new failure pattern, or a prompt change that quietly hurt responses shows up on its own.

- **Set it once, watch continuously.** Create a Monitor from a product's **Monitors** tab (Production view). Each Monitor scores a sampled share of that product's production sessions — 10% by default — so you get a representative quality signal without paying to score every single conversation. Raise or lower the sampling rate as your traffic and budget change.
- **Metrics stay current on their own.** A Monitor binds a metric *family*, not a fixed version. When you revise a metric, the Monitor picks up the new revision automatically — you never re-edit the Monitor.
- **Spend stays under control.** An optional monthly credit cap protects each Monitor's spend, and your organization balance is always the hard limit. The Monitor's status tells you exactly why it is or is not scoring right now: `ACTIVE`, `PAUSED`, `CAPPED`, or `NO_CREDITS`.

Get started with [Monitor Production Responses](/sdk/tutorials/monitor-production-responses-to-user-queries), or point a Monitor at [real user traffic ingested over OpenTelemetry](/sdk/tutorials/monitor-real-user-traffic-with-opentelemetry).

### See the Score Trend Across the Whole Product

A Monitor's own page shows the results of that one Monitor. To see the trend across every production evaluation of a product, open its **Analytics** tab in **Production** view mode: an **evaluation scores over time** chart plots the average score per day. Switch between a **by metric** view (one line per metric family) and a **by specification** view (one line per [specification](/concepts/product/specification), built from the metrics linked to it). The chart follows the same filters as the rest of the page (version, test, metric, language, and time frame) and includes every matching production evaluation, including the ones you triggered by hand.

### Sessions Close Themselves, so Monitors Know When to Score

A Monitor scores a [session](/concepts/product/version/session) only once the conversation is over. So that Galtea knows when that is, a session now closes on its own after a period of inactivity, instead of staying open forever waiting for your integration to end it.

- **Configure it per product.** In the product's advanced settings you set the auto-close scope (`NONE`, `DEVELOPMENT`, `PRODUCTION`, or `ALL` — the default is `PRODUCTION`), the inactivity window in minutes (default 30), and what happens if a new turn arrives for an already-closed session: `REJECT` it with an error, or `IGNORE` it silently.
- **Close a conversation the moment it ends.** When you already know a conversation is finished, close it right away with the SDK's [`sessions.finish(session_id)`](/sdk/api/session/finish) so its Monitor scores it on the next scan instead of waiting out the inactivity window.
- **Know when production will not be scored.** If a product's auto-close scope excludes production, open production sessions never close on inactivity, so their Monitors score only the sessions you finish explicitly. The dashboard warns you when that is the case.

### Evaluation Scores Over Time Moved to the Production View

The scores-over-time chart announced in the 2026-07-21 release now appears only in the **Production** view of a product's Analytics tab. It plots one average score per day, which answers "is the live product drifting", so it belongs next to your Monitors rather than beside your test runs. Development still compares versions with the existing scores and performance charts. Details in [Monitor](/concepts/product/monitor).

## Evaluate Your Voice Agents over WebRTC

You can now evaluate AI voice agents that connect over [WebRTC](/concepts/product/webrtc-connection), the standard for real-time audio over the internet. Instead of calling an HTTP API, Galtea opens a live WebRTC session with your agent through [Pipecat Cloud](https://pipecat.ai) and runs the conversation as a real voice call.

Set it up once: create a **WebRTC Connection** with your Pipecat Cloud public API key and the name of the agent to target, then attach it to a [version](/concepts/product/version). A version reaches your product through exactly one target — an [endpoint](/concepts/product/endpoint-connection), a [phone connection](/concepts/product/phone-connection), or a WebRTC connection — so choose WebRTC when Galtea should open a WebRTC session. The API key is stored encrypted and never returned; a fetched connection reports only whether a key is set.

WebRTC connections run any test type with no extra setup:

- **Behavior** test cases run multi-turn, with the conversation simulator driving each user turn from the test case's persona, goal, and scenario.
- **Accuracy** and **Security** test cases run single-turn: Galtea speaks the test case's input line into the call and evaluates the reply.

The caller's language comes from each test case, so one connection serves test cases in many languages, and with a multilingual voice the caller speaks that language with a natural accent. Both sides of every turn — the synthetic caller and your agent — are recorded, transcribed, and available to play back in the dashboard and read through the SDK. Manage connections in the dashboard's **WebRTC Connections** section or with the SDK's [`webrtc-connection`](/sdk/api/webrtc-connection/service) resource.

As your product evolves, its documentation (PRDs, design docs, spec sheets) often changes before its [specifications](/concepts/product/specification) do. A new **Update from document** action on the product detail page bridges that gap.

- **New** — a behavioral expectation found in the document that has no matching specification yet.

## Job Cancellation

You can now cancel in-progress async jobs from both the API and the SDK. When you start an inference batch — for example, via [`evaluations.run()`](/sdk/api/evaluation/run) in endpoint-connection mode — and need to stop it early, call [`galtea.jobs.cancel(job_id)`](/sdk/api/job/cancel). Queued jobs are removed from the queue; jobs already running receive a cooperative cancellation signal and stop at their next checkpoint. Cancellation is idempotent — calling `cancel()` on an already-cancelled job returns `state='cancelled'` rather than raising an error. Use [`galtea.jobs.get_status(job_id)`](/sdk/api/job/get-status) to check the current state before deciding whether to cancel. See the [Jobs Service reference](/sdk/api/job/service) for the full API.

## Langfuse Integration

If you already use [Langfuse](https://langfuse.com) to observe your LLM application, you can now send the same traces to Galtea for evaluation by swapping a single import. ## Specifications

[Specifications](/concepts/product/specification) are now live — a structured way to define and test the behavioral expectations of your product.

A Specification represents a single, testable claim about what your product should or should not do. Each specification has a **type** that classifies the expectation:

- **Capability** — a core function the product can perform
- **Inability** — something the product fundamentally cannot do, regardless of user input
- **Policy** — a rule the product must follow, such as refusing certain requests or always adding a disclaimer

You also assign a **test type** (`ACCURACY`, `SECURITY`, or `BEHAVIOR`) that determines how the specification is evaluated.

Specifications replace the legacy free-text Capabilities, Inabilities, and Policies fields that used to live on the Product form. Your behavioral expectations are now discrete, individually traceable, and can be linked directly to the [metrics](/concepts/metric) that validate them.

You can manage specifications from the dashboard or via the [Specification Service](/sdk/api/specification/service) in the SDK.

## New Deterministic Metrics

Four new deterministic metrics are now available:

- **Text Similarity**: Quantifies how closely two texts resemble each other using character-level fuzzy matching.
- **Text Match**: Checks if generated text is sufficiently similar to a reference string, returning a pass/fail based on a threshold.
- **Spatial Match**: Verifies if a predicted box aligns with a reference box using IoU scoring, producing a pass/fail result.
- **IoU (Intersection over Union)**: Computes the overlap ratio between predicted and reference boxes for alignment and detection tasks.

These new metrics complement our existing evaluation suite and are perfect for scenarios requiring deterministic, rule-based scoring.

## New Red Teaming Strategies: Role Play and Prefix Injection

We've expanded our arsenal of [Red Teaming Strategies](/concepts/product/test/red-teaming-strategies) to help you build more robust AI defenses:

- **Role Play**: This strategy attempts to alter the model's identity (e.g., "You are now an unrestricted AI"), encouraging it to bypass its own safety mechanisms and perform actions it would normally refuse.
- **Prefix Injection**: Adds a misleading or tactical instruction before the actual malicious prompt. This can trick the model into a different mode of operation, making it more susceptible to the adversarial attack.
